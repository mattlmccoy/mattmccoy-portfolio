Dear Machina Labs Hiring Team,

I'm applying for the Senior Product Manager role on the pre-cell software team. My background is unusual for a PM role: I'm a manufacturing engineer by training, a program manager by practice, and someone who has shipped software tools that process engineers and factory operators actually depend on. I've been on both sides of the digital-to-physical handoff that Machina Labs' path planning and simulation software is trying to solve, and that perspective is the main reason I'm writing.

Building Software That Manufacturing Teams Use

At Formlabs I led the factory test software team as part of my Technical Program Manager role on the Fuse 1+ 30W platform. That team was responsible for more than 150 acceptance tests run on every unit off the production line. I owned the software roadmap for that system: prioritizing what got built, sequencing it against production milestones, and working with the firmware and software engineers to ship features that factory operators could actually run without a manual. The constraint was always the same as any internal tooling PM faces: the users are captive, they'll tolerate rough edges up to a point, and then they'll find a workaround that makes the data unreliable.

Beyond the test software, I designed and shipped two customer-facing diagnostic tools that stayed in active deployment for more than three years. The first used purpose-designed calibration artifacts and an inexpensive caliper to reduce dimensional error by a factor of three, from ±300 µm to ±100 µm, without technician visits. The second detected thermal drift inside deployed machines using engineered geometric print artifacts. Both required the same PM discipline: understanding what the user was actually trying to accomplish, stripping the feature set down to what was essential, and shipping something reliable enough to trust at scale. The calibration tool enabled LEGO's global factory deployment of Fuse printers. That's the bar I hold tooling software to.

In my Ph.D. at Georgia Tech I've extended this further. I built an open-source scanner-based metrology toolkit used internally for jetting diagnostics and ink concentration analysis, and designed the HEATR simulation platform, a purpose-built 2.5D electrothermal simulation tool for rapid geometry and parameter space exploration. Both started as research infrastructure and ended up being the daily tools my collaborators and I depend on. Figuring out how to make a technically complex tool feel obvious to someone under deadline pressure is something I've been doing for years under a different title.

Program Management That Looks a Lot Like PM

My TPM role at Formlabs was, in practice, product management for a hardware program. I owned scope definition, prioritization across competing engineering workstreams, milestone planning, risk tracking, and stakeholder communication from the engineering floor to the executive team. Coordinating more than 130 engineering change orders through a full NPI cycle, across mechanical, electrical, firmware, software, and manufacturing process teams, is exactly the kind of cross-functional orchestration a senior PM runs day to day. We shipped the Fuse 1+ 30W in nine months from prototype to production. The software team was part of that, and keeping their roadmap in sync with hardware milestones was one of the harder parts of the job.

My doctoral research has added a different dimension: self-directed program management without structure. I pitched the RFAM concept, secured approximately $150,000 in funding including the NSF GRFP, scoped the full system architecture, and built the first platform from the ground up within a year. Managing what gets built when, against a research program that has no external forcing function except the one you create, builds a particular muscle for prioritization under ambiguity. That muscle is what early-stage internal tooling requires, where the roadmap is yours to define and the user feedback loop is brutally short.

Understanding the User from the Inside

The user Machina Labs needs this PM to serve is a process engineer trying to turn a CAD file into a robot program with confidence that it won't crash the toolhead or produce a bad part. I know that user because I've been that user. At Formlabs, the process engineers I worked alongside were dealing with exactly the same translation problem: a digital design with nominal geometry, a physical process with process-dependent deviation, and tooling software that bridged the gap with varying degrees of success. The moments where the software forced a workaround, or produced output the engineer couldn't interpret, or silently gave the wrong answer, were the moments that drove the most frustration and the most risk.

That understanding is hard to develop from a requirements document. It comes from running the process, reading the failure modes, and knowing which simplifying assumptions in the simulation actually matter in practice. My work on RF heating simulation (HEATR), laser path characterization at Formlabs, and in-situ imaging analysis in my Ph.D. all live in the same territory: computationally complex geometry and physics problems where the software has to give an engineer enough confidence to commit to a run. Building the product roadmap for Machina's path planning and simulation tools from that vantage point is a job I'd find genuinely challenging and worth doing.

Machina Labs is building the kind of factory I've been working toward in my research: software-defined, physically grounded, and fast enough to be useful before the design is stale. The pre-cell software is what makes that possible, and getting it right requires someone who understands the manufacturing problem at depth. I'd love to talk through the role in more detail.
